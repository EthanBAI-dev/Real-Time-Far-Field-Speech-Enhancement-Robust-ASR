## I-01 · 系统没有可用的 Python

- **状态**：✅ 已解决
- **阶段**：Phase 0 环境勘察
- **现象**：`python --version` 输出只有 `Python`，没有版本号；`where python` 指向
  `C:\Users\haku\AppData\Local\Microsoft\WindowsApps\python.exe`，文件版本 `0.0.0.0`。
- **根因**：这是 Windows 11 的 **Microsoft Store 占位存根（App Execution Alias）**，
  并非真正的 Python 解释器。直接执行会打开应用商店页面。系统中确实不存在任何真实 Python 安装
  （`C:\Users\haku\AppData\Local\Programs\Python`、`C:\Python*`、conda 目录均不存在）。
- **解法**：使用已安装的 **uv 0.11.3** 拉取独立的 Python 3.11 到项目虚拟环境，
  不去动系统 PATH，也不安装系统级 Python。所有命令统一走 `uv run`。

## I-02 · uv 自带的 Python 是 3.14，版本过新

- **状态**：✅ 已解决（通过版本锁定规避）
- **阶段**：Phase 0 环境勘察
- **现象**：`uv python list --only-installed` 只有 `cpython-3.14.3`。
- **根因**：Python 3.14 发布时间太近，音频/ML 生态（PyTorch、onnxruntime、pesq、
  numba/librosa 链路）在 Windows 上尚无对应 wheel。缺 wheel 会触发源码编译，
  而本机**没有 MSVC Build Tools**（见 I-03），编译必然失败。
- **解法**：`pyproject.toml` 中锁定 `requires-python = ">=3.11,<3.12"`，
  由 uv 自动下载独立的 CPython 3.11。3.11 是当前音频 ML 生态 wheel 覆盖最完整的版本。

## I-06 · sqrt-Hann 并非"天然满足 COLA"，只在 50% 重叠时增益才是 1

- **状态**：✅ 已解决（实现已泛化）
- **阶段**：Phase 2 信号核心
- **现象**：`STFTConfig(n_fft=512, hop=128)`（75% 重叠）构造时报
  `sqrt-Hann 在 hop=128 下不满足 COLA，偏差 1.000e+00`。
- **根因**：这是我最初实现里的一个真实局限，被测试逼出来了。
  sqrt-Hann 的"分析窗 × 合成窗 = 周期 Hann"，而周期 Hann 的重叠相加增益是
  **`n_fft / (2 * hop)`**，不是常数 1：
  | 重叠率 | hop | OLA 增益 |
  |---|---|---|
  | 50% | N/2 | 1.0 ✅ |
  | 75% | N/4 | 2.0 ❌ 整体放大一倍 |
  | 87.5% | N/8 | 4.0 ❌ |

  也就是说"sqrt-Hann 满足完美重构"这个说法只在 50% 重叠下成立，
  而这恰好是默认配置，所以初版代码一直是对的、局限也一直藏着。
- **为什么值得修**：低延迟场景很可能想换成 75% 重叠（帧移 8 ms）。
  如果那时才发现所有输出整体放大一倍，会先怀疑模型、怀疑掩码、怀疑归一化，
  很难第一时间怀疑到窗函数上。
- **解法**：`sqrt_hann(n_fft, hop)` 增加可选的 COLA 归一化，窗除以 `sqrt(增益)`。
  hop = N/2 时系数恰为 1，**默认配置的数值一个比特都没变**（原有测试全部照常通过）。
  同时对增益非常数的 hop 直接抛错，而不是悄悄产出错误结果。
- **回归测试**：`tests/test_stft.py::test_raw_sqrt_hann_gain_is_only_unity_at_50pct`
  显式断言未归一化时三种重叠率下的增益分别为 1 / 2 / 4，把这个误解钉死。
  另加 `test_perfect_reconstruction_at_other_hops` 验证换 hop 后仍能完美重构。

## I-07 · `write_audio` 的削波保护会静默改变幅度，污染非尺度不变指标

- **状态**：✅ 已解决
- **阶段**：Phase 1 环境自检
- **现象**：`rtse-doctor` 的 soundfile 往返检查报误差 `1.72e-01`，比 16-bit 量化上界
  （`1/32768 ≈ 3.1e-5`）大了近 4 个数量级，看上去像 libsndfile 坏了。
- **根因**：不是 soundfile 的问题，是**我自己写的检查信号会削波**。
  测试信号用 `standard_normal * 0.3`，正态分布尾部超过 `1/0.3 = 3.33σ` 的样本必然存在，
  于是 `write_audio` 的削波保护把整段信号等比缩小了。量到的 0.17 是**缩放增益**，
  不是量化误差。
- **真正的隐患**：这个自检 bug 顺带暴露了一个设计陷阱 ——
  `write_audio` 会**静默**改变绝对幅度。如果评测流程写成"增强 → 写盘 → 读回来算指标"，
  那么 SDR、SegSNR 这类**非尺度不变**的指标就会被这个增益系统性地压低，
  而 SI-SDR（尺度不变）却完全正常。届时会出现"SI-SDR 涨了但 SDR 掉了"的诡异现象，
  极难定位。
- **解法**：
  1. `write_audio` 改为**返回实际增益**，并加 `guard_clipping` 开关；
  2. 文档字符串里明确写死规矩：**指标一律在内存数组上计算，绝不写盘再读回**；
  3. doctor 的检查信号改用保证不削波的 `clip(normal*0.2, ±0.9)`，
     并同时断言"增益必须等于 1.0"，把削波路径和量化路径分开验证。
- **修复后**：往返误差 `3.05e-05`，正好贴着 16-bit 量化上界 —— 符合预期。

## I-08 · `torch.onnx.export` 需要单独安装 `onnx` 包

- **状态**：✅ 已解决
- **阶段**：Phase 1 环境自检
- **现象**：`OnnxExporterError: Module onnx is not installed!`
- **根因**：`onnx`（图定义/序列化）与 `onnxruntime`（推理引擎）是两个独立的包，
  后者**不依赖**前者。只装 onnxruntime 可以**加载**模型，但不能**导出**模型。
  这个区分很容易踩：本地只做推理时确实不需要 onnx，
  但项目里要做"流式导出 → 本地一致性校验"，导出侧就必须有它。
- **解法**：`pyproject.toml` 主依赖加 `onnx>=1.16`，并在注释里写明它不是传递依赖。
- **附带发现**：本机 onnxruntime 的可用 provider 只有
  `AzureExecutionProvider, CPUExecutionProvider`，**没有 CUDAExecutionProvider**
  （需要 `onnxruntime-gpu` 包）。这对本项目**不是问题，反而是想要的**：
  RTF 与延迟指标本来就应该在 **CPU 单线程**下测量才有部署参考价值。

## I-09 · WebRTC VAD 的帧长与本项目的帧移不兼容

- **状态**：✅ 已解决（加适配层）
- **阶段**：Phase 2 VAD
- **现象**：WebRTC VAD 只接受 **10 / 20 / 30 ms** 的帧，
  即 16 kHz 下的 160 / 320 / 480 样本。本项目帧移是 **256 样本（16 ms）**，不在允许列表内。
  直接喂会抛 `Error while processing frame`。
- **为什么不改帧移去迁就它**：256 的帧移是从 512 点 STFT（32 ms 窗、50% 重叠）推出来的，
  它同时决定了频率分辨率、模型输入形状、算法延迟预算。
  为了一个**对照基线**去动整条链路的地基，是本末倒置。
- **解法**：在 `WebRTCVAD` 内做适配层 —— 维持样本缓冲，每凑够 160 样本调一次 WebRTC，
  再把这一帧内产生的多个子判决归约成一个。
  归约用 **any（有一个算一个）而非 majority**：VAD 的漏检会直接导致丢字（CER 的删除错误），
  代价远高于误触发。
- **代价**：判决相对本帧最多滞后 96 样本（6 ms），已记入指标表。
- **附带修复**：转 int16 前必须先 `clip(-1, 1)`。增强后的信号偶有 |x| > 1 的样本，
  直接乘 32767 会**整数溢出绕回**，产生随机的错误判决 —— 这种 bug 表现为
  "VAD 偶尔莫名其妙抽风"，极难定位。已加回归测试。

## I-10 · VAD 门控硬切，把连续语音削出坑

- **状态**：✅ 已解决
- **阶段**：Phase 2 管线
- **现象**：测试 `test_pipeline_vad_gate_attenuates_silence` 失败 ——
  开启门控后，**语音段**的 RMS 掉到了未门控时的 **0.68**，即被削掉了三成能量。
- **根因**：初版实现是硬切：`if not is_speech: spec *= gate_floor`。
  增益在 1.0 和 0.1 之间**逐帧瞬间跳变**。两个后果：
  1. 每次跳变是一个阶跃，听感上是"咔哒"声；
  2. VAD 在音节间隙（尤其是清音、词间停顿）难免短暂翻转，
     硬切会把本该连续的语音削得坑坑洼洼 —— 测出的 0.68 就是这么来的。
- **解法**：改为**非对称一阶平滑（快开慢关）**，这是噪声门的标准做法：
  - 打开时间常数 **5 ms**：语音起始必须立刻放行，慢了就是丢字；
  - 关闭时间常数 **200 ms**：慢关同时充当"软挂起"，
    自然吸收 VAD 在音节间隙的短暂翻转。
  另外初始状态设为**全开**，避免开头第一个字被门控吃掉。
- **修复后**：语音段比值回到 0.9 以上，静音段仍被压到 0.5 以下，测试通过。
- **更一般的教训**：任何"按帧开关"的逻辑（门控、模型热切换、增益跳变）
  都需要时间常数平滑。帧级的布尔量直接乘到信号上，在音频里几乎总是错的。

## I-11 · 控制台代码页是 cp932（日文），print 中文直接崩溃

- **状态**：✅ 已解决
- **阶段**：Phase 6 Web 服务
- **现象**：`uv run rtse-server` 连启动都启动不了：
  ```
  UnicodeEncodeError: 'cp932' codec can't encode character '实'
  in position 2: illegal multibyte sequence
  ```
- **根因**：**这台机器的 Windows 控制台代码页是 cp932（日文 Shift-JIS）**，
  既不是 UTF-8 也不是简体中文的 GBK。Python 的 `sys.stdout` 默认按控制台代码页编码，
  于是任何一个中文字符都编不出去，直接抛异常终止进程。
  （从 `Y:` 盘的目录名"図面/試作図"也能印证这是台日文环境的机器。）
- **为什么 `rtse-doctor` 没崩**：它的输出全部走 `rich.Console`。
  rich 在 Windows 上用的是控制台 API 而不是字节流，天然绕开了代码页问题。
  只有裸 `print()` 会中招 —— 所以这个坑是**随机触发**的，取决于哪个模块用了裸 print。
- **解法**（两层，缺一不可）：新增 `src/rtse/cli/_console.py`
  1. **防崩溃**：`sys.stdout/stderr.reconfigure(encoding="utf-8", errors="replace")`。
     最坏情况显示成问号，但**绝不会因为编码而挂掉**。这层能兜住第三方库里我们管不到的 print。
  2. **防乱码**：所有面向用户的输出统一走 `rich.Console`，正确渲染非 ASCII。
- **推广**：新写 CLI 一律 `from rtse.cli._console import console`，不要用裸 `print`。

## I-12 · 频谱图整片洗白：dB 参考点没有定义

- **状态**：✅ 已解决
- **阶段**：Phase 6 Web 可视化
- **现象**：文件实验台的频谱图看不出任何结构。像素统计显示中位亮度
  **227 / 245**（最大值），连 1% 分位都有 107 —— 整幅图压在色标顶端，一片均匀亮黄。
- **根因**：我按"时域信号在 ±1 之间，所以 dB 应该是负的、接近 0"的直觉
  去定色标范围（-85 ~ -5 dB）。**这个直觉是错的。**
  `|rfft(frame * window)|` 是 512 个加窗样本的**相干求和**，量级远大于时域幅度：
  实测一个峰值 1.0 的正弦在对应频点上的 STFT 幅度是 **162.97**，即 **+44 dB**。
  于是所有真实数据都远高于色标上限 -5，全部被钳到最亮色。
- **解法**：在 `rtse/audio/stft.py` 里显式定义 dB 参考点：
  ```python
  spec_ref(cfg) = sum(window) / 2   # 满幅正弦在其频点上的 STFT 幅度
  magnitude_db(spec) = 20*log10(|spec| / spec_ref)
  ```
  归一化后**满幅正弦精确读到 0.0 dBFS**，幅度减半精确对应 −6.02 dB。
  实测语音的频点分布：p10 ≈ −90、p50 ≈ −70、p99 ≈ −30 dBFS，
  据此把色标定为 **−90 ~ −20 dBFS**。修复后像素分布 p10=14 / p50=90 / p90=178，
  动态范围完全打开，而且能直接看出降噪效果（带噪 p50=118 → wiener p50=90）。
- **关键点**：`magnitude_db` 是**全项目唯一**的谱转 dB 入口，
  实时管线、文件实验台、评测器必须都调它。各处自己写 `20*log10(abs(spec))`
  是"两幅频谱图对不上"的头号原因。
- **回归测试**：`test_magnitude_db_is_calibrated_to_dbfs` 断言满幅正弦 = 0 dBFS
  且 −6.02 dB 的半幅关系。这个标定一旦漂移，前端色标和报告里所有 dB 数字都会跟着错，
  而且**不会报错**，只是"图看起来偏亮"—— 必须用测试钉死。

## I-13 · 改了 Python 代码但服务端没重启，白排查了一轮

- **状态**：✅ 已解决（记为流程教训）
- **阶段**：Phase 6
- **现象**：修好 I-12 的归一化后，前端频谱图**依然**洗白。一度怀疑是浏览器缓存了旧 JS、
  怀疑 max-pooling 抬高了数值，排查了一圈才发现：**uvicorn 没开 `--reload`，
  服务端还在跑改动前的 Python 代码**。
- **教训**：前后端一起改的时候，"改了没生效"有三个独立的嫌疑源 ——
  浏览器 JS 缓存、服务端进程未重启、以及真的没改对。
  排查顺序应该是**先确认代码真的生效**（重启 + 硬刷新），再去怀疑逻辑。
- **落地**：`.claude/launch.json` 里的开发配置保持不带 `--reload`（避免文件监听在
  网络盘上出怪问题），但**每次改完 Python 必须重启服务**。
  `rtse-server --reload` 可用于纯前端联调阶段。

## I-14 · torch 与 numpy 的 STFT 对不齐（两个独立问题）

- **状态**：✅ 已解决
- **阶段**：Phase 4 训练侧代码
- **背景**：训练在 torch 里做 STFT，推理在 numpy/ONNX 里做。两者只要不一致，
  模型见到的输入分布就与部署时不同 —— 症状是"验证集很好、一上线掉点"，
  而且**两边单独看都没问题**，极难定位。所以这条一定要用测试钉死。

### 问题 A：`torch.istft` 与"裸重叠相加"的约定不兼容

- **现象**：`RuntimeError: ... window overlap add min: 1`，直接抛错。
- **根因**：两点叠加：
  1. `torch.istft` 会做**窗和归一化**（除以 `sum(w²)` 的包络），
     而本项目的约定是**裸 OLA 不归一化** —— 因为流式 iSTFT 没有能力做全局归一化，
     只有两边都裸 OLA 才可能逐样本一致（见 `audio/stft.py` 的设计说明）。
  2. 它强制 **NOLA 检查**。sqrt-Hann 首尾样本的窗值为 0，`center=False` 下
     边缘帧的窗和必然为 0，检查必挂。
- **解法**：不用 `torch.istft`，改用 `F.fold` 手写重叠相加。
  这既绕开了 NOLA 检查，也保证了与 `rtse.audio.stft.istft` 是**同一个算法**。

### 问题 B：帧数少算一帧，尾部 256 个样本重建不出来

- **现象**：修好 A 之后，STFT 对拍✅、iSTFT 对拍✅，但 **torch 侧完整往返**
  的相对误差 **5.3e-2**。
- **根因**：`stft_torch` 里我自己推了一遍帧数公式，得到 32 帧，
  而 numpy 版的 `num_frames()` 给的是 33 帧。少的那一帧正好覆盖信号尾部，
  于是最后约 256 个样本没被重建。
- **为什么两个对拍测试都没抓住**：它们比较的是**重叠部分**，
  而重叠部分确实完全一致。我当时还把帧数断言放宽到了 `±1`，
  正好把这个 bug 放过去了。
- **解法**：
  1. `stft_torch` 直接调用 numpy 版同一个 `num_frames()`，不再自己推公式；
  2. 把测试里的帧数断言从 `±1` 收紧到**精确相等**；
  3. 新增 `test_torch_roundtrip_reconstructs` —— **完整往返**才是真正的判据，
     分段对拍会漏掉边界问题。
- **教训**：两套实现对齐时，"分别对拍各个环节"不足以保证端到端一致。
  必须有一条**端到端**的测试，而且断言里任何"放宽容差"的地方都要有明确理由 ——
  这里的 `±1` 就是随手写下的，代价是多花了一轮排查。

## I-15 · 训练数据的随机增益仍会削波

- **状态**：✅ 已解决
- **阶段**：Phase 4 训练侧代码
- **现象**：`test_never_clips` 失败 —— 训练样本峰值 **1.0161**，超过满幅。
- **根因**：削波保护写成了
  ```python
  scale = gain / peak * 0.9 if peak * gain > 0.99 else gain
  ```
  看上去是"会削波就归一到 0.9"，实际结果峰值是 `gain * 0.9`。
  而随机增益上限是 **+3 dB（1.41 倍）**，于是 `1.41 × 0.9 = 1.27` —— 仍然削波。
  更糟的是这个分支**经常被触发**（只要原始峰值稍大就会进来）。
- **危害**：削波过的训练输入与推理时见到的输入分布不同，
  模型会学到一个不存在的"输入总是被压平"的先验。这类问题不会报错、
  loss 曲线也看不出来，只会体现为最终指标差一截。
- **解法**：削波分支直接按峰值归一，与 `gain` 无关：
  ```python
  scale = gain if peak * gain <= 0.99 else 0.9 / peak
  ```
- **回归测试**：`test_never_clips` 跑 200 个样本断言最大峰值 ≤ 1.0。
  用 200 个而不是 1 个，是因为这个分支的触发依赖随机增益，单样本抽不到。

## I-16 · 本机没有可用的麦克风，而报错信息把人往错方向引

- **状态**：✅ 已解决（含一个功能补强）
- **阶段**：Phase 6 Web 演示
- **现象**：点「开始」后报 `麦克风授权失败：NotFoundError`，
  紧跟着我写的提示「浏览器只在 localhost 或 HTTPS 下允许访问麦克风」。
- **两个问题**：

### 问题 A：报错信息是错的

`NotFoundError` 的含义是**没找到匹配的设备**，与来源安全性完全无关
（那是 `NotAllowedError` / `SecurityError`）。我不分错误类型一律提示 HTTPS，
会让人去折腾根本没问题的证书和端口号。

**实测确认**（PowerShell + 浏览器双向验证）：

| 端点 | 状态 |
|---|---|
| `マイク (Realtek(R) Audio)` | **Unknown** ← 未接入 |
| `スピーカー (Realtek(R) Audio)` | OK |
| `VL-B24W-9T (NVIDIA HD Audio)` | OK |

麦克风隐私设置是 `Allow`（HKLM 与 HKCU 均是），浏览器
`enumerateDevices()` 返回的 `audioinput` 数量为 **0**。
即：台式机的 Realtek 麦克风插孔没插东西，Windows 隐藏了该端点，
浏览器确实看不到任何录音设备。

**解法**：
1. 按 `DOMException.name` 逐一给出**准确**诊断
   （NotFound / NotAllowed / NotReadable / OverConstrained 各不相同），
   并把当前系统报告的输入设备数一起显示出来；
2. 页面加载时就**主动探测**设备（`enumerateDevices` 在未授权时
   label 为空但**条目仍在**，足以判断有无），而不是等用户点了才失败；
3. 顺带放宽约束：`sampleRate` 从精确值改为 `{ ideal: 16000 }`。
   写成必须满足的约束时，若无设备支持该采样率浏览器会直接抛错，
   而不是让 AudioContext 去重采样。

### 问题 B：没有麦克风就完全用不了，这本身不合理

作品集演示时未必总有麦克风。**新增「虚拟麦克风」**：
服务端按指定条件（噪声类型 / SNR / T60）合成音频，前端按**真实时间节奏**
（每 128 ms 一块）推进同一条 WebSocket 路径。

关键点：**不能一次性全发**。那样服务端会在几十毫秒内处理完 20 秒音频，
测出来的 RTF 和延迟就变成了批处理吞吐量，与实时部署毫无关系。
按真实节奏推送后，RTF 与 p95/p99 指标与真麦克风**等价**。

合成放在服务端而不是浏览器，是为了让"0 dB"在虚拟麦克风、文件实验台、
Colab 训练三处是**同一个定义**（都走 `mix_at_snr`）。

检测到无输入设备时自动切到该模式并说明原因。

## I-17 · 静态资源被浏览器缓存，改了前端刷新没反应

- **状态**：✅ 已解决
- **阶段**：Phase 6
- **现象**：改完 `live.js` 重启服务、刷新页面，**新的 HTML 生效了、JS 却还是旧的**。
  实测：浏览器手上的 `live.js` 是 6293 字节，服务端实际是 11078 字节。
  症状极具迷惑性 —— 页面上多出来的控件都在，但点了没反应。
- **根因**：Starlette 的 `StaticFiles` 只发 `ETag` 和 `Last-Modified`，
  **不发 `Cache-Control`**。缺了它，浏览器启用*启发式缓存* ——
  按 Last-Modified 的时间差自己估一个过期时间，在此期间**连条件请求都不发**，
  直接用本地副本。所以不是"服务端返回了旧文件"，是**请求压根没发出去**。
  （`location.reload(true)` 的 `true` 参数在现代 Chrome 里已被忽略，不能用来绕过。）
- **解法**：加中间件，给页面与 `/static/*` 统一发
  `Cache-Control: no-cache, must-revalidate`。
  用 `no-cache` 而不是 `no-store`：前者只是强制**每次都验证**，
  ETag 未变时仍回 304，几乎没有额外开销。
- **与 I-13 的关系**：这两条是同一个陷阱的两层。I-13 是服务端进程没重启，
  I-17 是浏览器根本没发请求。**"改了没生效"有三个独立嫌疑源**：
  浏览器缓存、服务端进程、代码本身。排查顺序应当是先确认前两个，再怀疑逻辑。
  现在两层都从根上堵掉了。

## I-18 · 实时电平读数是瞬时值，摆动到毫无参考价值

- **状态**：✅ 已解决
- **阶段**：Phase 6
- **现象**：同一个方法（wiener），「净衰减」读数一会儿 0.1 dB、一会儿 16.3 dB，
  看起来像功能坏了。
- **根因**：服务端给的 `in_db` / `out_db` 是**每 128 ms 一块的瞬时 RMS**。
  这一块恰好落在语音段还是静音段，读数能差十几 dB。直接显示瞬时值没有意义。
- **解法**：
  1. 前端加一阶平滑，时间常数约 **1.6 s**（`TAU=0.92`）。
     **平滑必须在 dB 域做** —— 在线性域平滑再取对数的话，
     少数几个高能量块会主导结果，静音段的信息几乎被抹掉。
  2. 时间常数不能给太大：一开始用 0.98（≈6.4 s），读数是稳了，
     但切换方法后要等六七秒才爬到新值，用起来像"切了没反应"。
  3. 切换方法时**一并重置平滑状态**，避免从旧值慢慢爬过来。
  4. 静音块（< −80 dB）不参与平滑，否则一段静音就能把读数拖到底。
- **修复后**：连续采样 20 秒得到 7.6 ~ 13.3 dB（均值 9.8），平滑漂移无跳变。
- **附带发现**：切换方法后头几秒读数确实偏低，这**不是** bug ——
  管线重建时 MCRA 噪声估计器被重置，需要约 2 秒重新建立最小值跟踪窗口。
  这是真实且正确的行为，但界面上不说清楚就像坏了，已在指标说明里写明。
- **另外**：「净衰减」只说明**动了多少，不说明动得对不对** ——
  无差别把所有声音压低 10 dB 也能得到 10 dB。已在界面上标注，
  并引导到文件实验台看有参考的 SI-SDR / STOI。

## I-19 · 卷混响用了直接卷积，训练时数据加载会彻底卡死

- **状态**：✅ 已解决
- **阶段**：Phase 4 训练数据管线
- **怎么发现的**：用户问「Colab 免费版该选哪个 GPU」。免费版只有 **2 个 vCPU**，
  这促使我去核对数据加载能不能喂饱 GPU —— 一测就撞上了。
- **现象**：`apply_rir` 用 `np.convolve` 做直接卷积，耗时随 RIR 长度爆炸：

  | T60 | RIR 长度 | `np.convolve` | `fftconvolve` | 倍数 |
  |---|---|---|---|---|
  | 0.3 s | 6560 | 42 ms | 1.7 ms | 25× |
  | 0.6 s | 12320 | **6996 ms** | 2.0 ms | **3482×** |
  | 0.9 s | 18080 | **7845 ms** | 2.1 ms | **3781×** |

  （4 秒音频段，i7-14700 实测）

- **根因**：直接卷积是 O(n·m)。训练配置里 `reverb_prob=0.5`、
  T60 从 `uniform(0.2, 0.8)` 采样，**约一半样本会落进秒级路径**。
  按平均 3.5 秒/样本、2 个 worker 算，一个 20000 样本的 epoch
  光数据加载就要 **约 5 小时**，GPU 全程空转。
- **为什么危险**：**不会有任何报错**。表现只是"训练慢得离谱"，
  而人的第一反应通常是怀疑 GPU 不够快、去换更贵的运行时 ——
  方向完全错了。在 Colab 上这意味着白白烧掉几小时配额。
  注意 42 ms → 6996 ms 只对应长度翻一倍，中间有个断崖式的跳变
  （numpy 掉出了某条快路径），所以拿 T60=0.3 试一下会觉得"还行"，
  真正跑起来才炸。
- **解法**：改用 `scipy.signal.fftconvolve`，并把 import 提到模块级
  （放在函数里会让首次调用多花 1~2 秒导入 scipy，容易被误读成"合成很慢"）。
  数值完全等价（实测偏差 < 1e-9 相对）。
- **修复后实测**（单样本合成耗时 / 2 worker 吞吐 / 20000 样本 epoch 的加载时间）：

  | reverb_prob | 单样本 | 吞吐 | epoch 加载 |
  |---|---|---|---|
  | 0.0 | 3.5 ms | 571/秒 | 0.6 分钟 |
  | 0.5（默认） | **5.1 ms** | 393/秒 | **0.8 分钟** |
  | 1.0 | 5.4 ms | 371/秒 | 0.9 分钟 |

  即便 Colab 的 CPU 比本机慢 3 倍，也只是 2~3 分钟/epoch，**不再是瓶颈**。
- **回归测试**：`test_apply_rir_is_fast_enough_for_training` 断言
  T60=0.6 时耗时 < 50 ms（FFT 约 2 ms，直接卷积约 7000 ms，
  中间隔三个数量级，不存在误判）。
  另加 `test_apply_rir_matches_direct_convolution` 保证提速没改变结果。
- **更一般的教训**：性能问题要有**测试**来守，不能只靠"跑起来感觉还行"。
  这一条如果不是被问到 vCPU 数量，很可能要到 Colab 上烧掉几小时才发现。

## I-20 · MCRA 噪声估计在高输入 SNR 下系统性失真，把语音功率误吸收成噪声

- **状态**：🔶 **部分解决**——主要失效模式（混响+高SNR）已修复并用真实数据验证；
  一个更深层的次要问题（短促静音间隙场景）确认无法靠调参解决，仍未解决
- **阶段**：Phase 5 本地评测（用 Colab 训练+评测产出的真实测试集数据发现）
- **发现契机**：用户跑完 `03_export_eval.ipynb` 贴出的汇总表里，DSP 三个方法
  （specsub/wiener/mmse-lsa）的 SI-SDR 全部**低于不处理**（none=2.80，wiener=1.35）。
  写进 `METRICS.md` 前按 SNR/噪声/T60 分层复核，发现 SNR≥15 dB 时 DSP 方法的 SI-SDR
  **集体跳水到大幅负值**（SNR=10 时 wiener 平均 +12.06，SNR=15 骤降到 -5.92，
  SNR=20 为 -3.93），而"不处理"本身的 SI-SDR 在这个区间是正常上升的——处理完反而
  比不处理差一大截，且随 SNR 升高越处理越差，方向完全反常识。
- **排查过程**（每一步都是实测，不是猜）：
  1. 先怀疑是均值被离群点带偏——取 20 个样本逐个看，**20/20 全部一致变差**，
     幅度集中在 -3~-11 dB，排除"个别样本崩了"。
  2. 换白噪声、hum 分别测，效果**跨噪声类型完全一致**（SNR=15 时平均 delta 都在
     -7.5~-9.7 之间，SNR=20 时都在 -12.8~-13.3），排除"某种噪声类型特有"。
  3. 追进 `MCRANoiseEstimator` 内部状态：SNR=20 时真实噪声功率 `5.8e-4`，
     MCRA 最终估计出的噪声功率均值 `24.97`——**差了约 43000 倍**。
  4. 逐帧打印单个频点的 `S`（平滑功率）/`S_min`（局部最小值）/`ratio`/`indicator`：
     发现在明显有语音活动的一段（S 持续 2~4 倍于 S_min），`ratio` 长时间停留在
     1.6~3.6，**始终够不到 `delta=5.0` 这个"判定为语音"的门槛**，于是这些帧被
     误判为噪声，`noise = 0.95*noise + 0.05*power` 用语音功率持续小幅拉高噪声估计。
- **根因**：`delta=5.0`（Cohen & Berdugo 论文的标准取值）在当前的
  `alpha_s=0.8` 时间平滑 + 该测试信号的动态范围组合下，不足以可靠地把语音帧的
  `ratio` 推过判决门槛。SNR 越高，真实噪声本来就越安静，"语音功率被小比例
  持续吸收进噪声估计"这个偏差在**相对幅度**上越显著，且没有触发正确检测的窗口期
  越长（`L=125` 帧 ≈ 2 秒才重置一次），偏差有更多时间累积——这解释了为什么问题
  specifically 在高 SNR 下最严重。
- **影响范围（已精确圈定）**：
  - 只影响**共用 MCRA 的三个 DSP 方法**（specsub / wiener / mmse-lsa），
    且**只在 SNR ≥ 15 dB** 的格子里失真。
  - **神经网络模型（crn-nano/lite/large）完全不受影响**——它们不经过 MCRA，
    是独立的推理路径。
  - 排除 SNR≥15 后重新聚合（540/780 样本），DSP 方法恢复正常、显著为正：
    | method | SI-SDR (全部780) | SI-SDR (仅SNR<15,540) |
    |---|---|---|
    | none | 2.80 | 0.85 |
    | specsub | 1.57 | **3.65** |
    | wiener | 1.35 | **3.38** |
    | mmse-lsa | 1.38 | **3.39** |
    这和 Phase 2 本地冒烟测试（当时只测了 0dB/5dB）测出的 +2.9~+5.5 dB 量级一致，
    说明 bug 只存在于当时从未测过的高 SNR 区间。
  - **为什么 Phase 2 没抓到**：那时的本地冒烟测试（`smoke_dsp.py`）只跑了
    白噪声/babble/keyboard 在 0dB/5dB 两个 SNR 下的结果，从未探到 15dB/20dB——
    测试覆盖范围的盲区，不是代码逻辑第一次出现的时间点晚。
### 系统性参数验证（用户明确要求"认真修，不是几分钟的事"之后做的）

**第一步：先把"真值"算准。** 之前对照用的是时域功率乘个粗略系数
（`np.mean(scaled**2) * n_fft`，代码注释里自己写着"粗略量级"），精度不够指导调参。
改为把**纯噪声单独过一遍 STFT**，逐帧功率谱取均值，作为频域真值。

**第二步：网格搜索 delta × alpha_s。** 结果是**误差几乎不动**：

| alpha_s | delta | SNR=0 | SNR=5 | SNR=10 | SNR=15 | SNR=20 |
|---|---|---|---|---|---|---|
| 0.8（原） | 5.0（原） | 4.42 | 8.05 | 12.62 | 17.47 | 22.40 |
| 0.5 | 1.5（比标准值激进得多） | -2.54 | 1.34 | 7.44 | 11.50 | 15.09 |

即使把 delta 压到远低于文献标准值（5.0 → 1.5）、alpha_s 也大幅调低，SNR=20 时
误差依然有 15dB，且已经开始损害低 SNR 下的准确度（SNR=0 从 +4.4dB 矫枉过正到
-2.5dB）。**结论：这不是"两个常数调歪了"，是判决机制的结构性缺陷**——
这也是 Cohen 在 2002 年提出 MCRA 之后，2003 年又发表改进版 IMCRA 的原因。

**第三步：定位到底哪个统计量在骗人。** 检查 `S_min`（局部最小值追踪本身）
单独对比真值，发现**它也一样跟不上**（SNR=20 时仍有 20.4dB 误差）——问题比预想
的更底层：不是"判决门槛不对"，是**局部最小值追踪在当前 2 秒窗口内根本没有
机会探到真正的地板**。

**第四步：定位为什么探不到。** 对比同一段语音的**带混响版本**和**无混响版本**：

| | SNR=0 | SNR=5 | SNR=10 | SNR=15 | SNR=20 |
|---|---|---|---|---|---|
| 带混响（T60=0.3） | 4.4 | 8.1 | 12.6 | 17.5 | 22.4 dB |
| 无混响 | 0.7 | 1.5 | 3.0 | 5.0 | **7.9 dB** |

**去掉混响后 SNR=20 的误差从 22.4dB 骤降到 7.9dB**——混响拖尾把词间停顿填上了
残余能量，最小值追踪找到的其实是"混响尾巴的地板"，不是真实的加性噪声地板。
剩下 7.9dB（无混响仍然存在）来自另一个更基础的原因：真实连续语音本身很少有
`speech_active_mask` 判定意义上的深度静音（THCHS-30 测试片段实测**静音占比 0%**），
供 MCRA 校准的"纯噪声时刻"本来就稀缺。

### 修复方案：双时间尺度最小值跟踪

在原有 `L=125` 帧（2秒）短窗口之外，并行跑一个 `L2=1000` 帧（16秒）的长窗口，
两者用同样的双缓冲重置机制，取**两者中更低的**作为最终地板。原理：混响污染或
真实语音的稀疏静音，2 秒内可能一次真正安静的机会都没有，但拉长到 16 秒，
遇到足够低点的概率大得多；同时长窗口依然会周期性重置，不会永久冻结，
保留了对**真实上升噪声**的适应能力（这是"直接用全局不重置的最小值"这个更简单方案
被放弃的原因——那样效果同样好，但录音环境如果后期真的变吵会永远追不上）。

这个修复**数学上是安全的**：`floor = min(短窗口, 长窗口)`，长窗口只可能让地板
更低或相等，不可能让原本正常工作的场景变得更差——`test_mcra_dual_timescale_never_increases_estimate`
把这条不变量钉成了测试。

**用真实 Colab 测试集数据验证（10 个随机样本，跨 SNR/噪声类型）**：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| cafeteria SNR=20（最严重的样本） | **-4.79 dB** | **+8.01 dB** |
| white SNR=0 | -0.13 dB | +2.00 dB |
| white SNR=0（另一样本） | -2.32 dB | +1.26 dB |
| 10 样本均值 | 2.32 dB | 4.17 dB |
| 原本已经正常的场景（SNR 10、-5 等） | 无明显变化 | 无明显变化，没有此消彼长 |

在完整 780 样本本地测试集上重算（wiener，按 SNR 分层，修复前 vs 修复后）：

| SNR | 修复前 | 修复后 |
|---|---|---|
| -5 | -6.06 | -5.52 |
| 0 | -1.30 | -0.57 |
| 5 | 6.81 | 7.18 |
| 10 | 12.36 | 12.55 |
| **15** | **-1.71** | **+7.25** |
| **20** | **-4.74** | **+9.49** |

高 SNR 的两格从大幅负值转正，低/中 SNR 几乎不变——修复精确命中了目标失效区间，
没有波及其他场景。**全量 780 样本汇总**（不再需要像之前那样排除 SNR≥15）：
specsub 5.11dB、wiener 5.23dB、mmse-lsa 5.22dB——已写入
`results/dsp_fixed_metrics.json`，`METRICS.md`/`FINDINGS.md` 同步更新。

### 仍未解决的部分（诚实记录，没有回避）

用 `speech`（单元测试用的合成夹具，含两段明确的长静音）在 SNR=20 白噪声下测试，
双时间尺度修复**没有效果**（依然是 -12.4dB，跟修复前几乎一样）。追查发现：
这段静音期间，语音判决**是正确的**（`indicator=0`），最小值追踪也**正确探到了**
真实地板——但噪声估计值本身收敛太慢：`alpha_d=0.95` 意味着每帧只吸收 5% 新信息，
30 帧（480ms）的静音段不够把估计值从残留的高位拉回真实地板。

尝试把 `alpha_d` 调低（加快收敛）验证这个假设，结果**适得其反**——在合成夹具上从
-12.43 恶化到 -13.74（alpha_d 从 0.95 降到 0.80），在真实数据 10 样本均值上只有
微弱改善（3.40→3.66）。原因：调低 alpha_d 是双向的，语音判决出现假阴性
（漏判为噪声）的帧也会更快地把估计值拉向错误方向，抵消了真正静音期间收敛变快的
好处。**结论：这不是简单调参能解的，需要比"改一个系数"更深层的改动**
（比如 IMCRA 式的软判决/贝叶斯语音存在概率，而不是硬阈值 + 固定速率递归平均）。

这个残留问题在**真实项目数据**上的实际影响看起来比这个极端合成夹具小得多——
真实语音的静音间隙分布在整段录音里到处都是（哪怕每次都很短、都不够深），
累积起来仍然给了递归平均足够的收敛机会；本次合成夹具刻意构造成"只有两段
高度集中的长静音"，是比真实场景更极端的边界情况。这从"真实 780 样本全量转正"
和"极端合成夹具依然失败"这两个并存的事实能看出来。

- **当前绕行**：无需绕行——`METRICS.md` 的 DSP 数字已经是修复后的全量结果，
  不再需要像之前那样把 SNR≥15 单独摘出去标注"不可信"。
- **回归测试**：
  - `test_mcra_dual_timescale_never_increases_estimate` —— ✅ 通过，
    验证修复的数学安全性（不可能让原本正常的场景变差）
  - `test_mcra_high_snr_known_bug` —— 仍然 `xfail`（如实反映残留问题未解决），

## I-21 · 测试集参考文本比截断后的音频长，CER 会系统性偏高

- **状态**：✅ 已定位并修复（notebook 已改好），⏸️ **本地测试集需要重新生成**
  （旧的 780 样本已知有问题，不能用来算 CER）
- **阶段**：Phase 5，接入真实 faster-whisper 做端到端转写验证时发现
- **发现契机**：ASR 模块（`src/rtse/asr/`）写完后，用本地测试集的几条高 SNR
  干净样本做真实转写验证（不是纸面上验证 API 契约，是真的跑一次模型看输出）。
  第一条样本转写完，CER 报出 0.844——远超预期。逐字对比参考文本和识别结果：

  ```
  参考: 硬骨头六连历任主管战斗英雄和转业退伍干部战士代表应邀坐在嘉宾席上
  识别: 印骨头六连立任主管，战斗英雄和转业……战士代表。
  ```

  "战斗英雄和转业"这几个字识别得完全正确，但参考文本后半段"退伍干部……
  应邀坐在嘉宾席上"在识别结果里**完全没有出现**——不是识别漏掉了，
  是音频里**根本没有这段内容**：测试集合成时把每条语音硬截成固定 6 秒
  （`clean[:seg_len]`），但参考文本（`text` 字段）用的是 THCHS-30 的
  **完整原句**，句子一旦超过 6 秒就被从中间切断，识别模型只能对着
  被切掉的音频转写，跟完整原句比对自然会出现大段"缺失"，被 CER 算成错误。
- **排查**：写了个用 VAD 检测"参考音频最后 0.5 秒是否仍处于说话状态"的
  抽查脚本，跑了 20 条高 SNR 样本——**20/20 全部命中**，全部在 6 秒截止点
  仍在说话。不是个别长句子的边缘情况，是整个测试集普遍存在的系统性问题。
- **影响范围**：污染的是**所有**780 个样本的 `text` 字段可用性，跟降噪方法、
  噪声类型、SNR 都无关——任何用这批测试集算出来的 CER 都不可信，
  已实测的 SI-SDR/STOI/ESTOI/PESQ 不受影响（那些指标比较的是音频本身，
  不涉及文本对齐）。
- **根因**：测试集生成时，音频截断长度（固定 `SEG_SEC=6.0`）和参考文本
  （完整原句，长度不定）是两个独立决定的量，没有互相校验过。
- **修复**：`01_data_prep.ipynb` 的测试集构建改成**按每条语音的自然时长**
  生成片段，不再硬截成固定秒数：
  1. 每条语音先读出真实时长，夹在 `[MIN_SEG_SEC=3.0, MAX_SEG_SEC=18.0]` 之间
     （比 THCHS-30 观察到的最长句子还留了余量），短的垫零，正常长度的完整保留；
  2. 万一某条语音自然时长仍超过 18 秒（理论上不该发生），换取样序列里下一条，
     而不是静默截断产生错位数据；
  3. **生成后立刻用 VAD 抽查**（末尾是否还在说话），断言抽查样本里 0 条截断，
     不通过就直接报错，不允许带着这个问题继续往下生成。这条校验是从这次调试
     过程直接搬进 notebook 的——不能只在本地事后发现问题，源头就要拦住。
- **代价**：体积会比固定 6 秒时略增（THCHS-30 句子普遍长于 6 秒，之前是把
  内容截短了、不是相反），仍在本地 < 2GB 的预算内；总处理时间基本不变
  （逐条按需时长处理，不是所有条都跑满 18 秒）。
- **当前状态**：notebook 已经改好、本地已用生成器脚本重新验证过语法，
  但**旧的 780 样本本地测试集是用修复前的逻辑生成的，不能直接拿来算 CER**——
  需要重新跑一遍 `01_data_prep.ipynb`（Drive 上语料压缩包还在，hybrid 模式下
  只是重新解压+重新合成，不用重新下载），把新的 `testset.zip` 传回本地覆盖。
- **教训**：这类"数据两个字段各自看起来都对，但互相之间没校验过"的 bug，
  只看汇总指标（比如"780 个样本，都有 text 字段"）完全发现不了，
  必须真的跑一次下游任务、盯着具体的输入输出对比，才会暴露。
  DSP/STOI/PESQ 这些指标从合成阶段起就一直在跑、一直"看起来没问题"，
  恰恰是因为它们不依赖文本对齐，才让这个问题潜伏了这么久没被发现。

- **第二次踩坑：修复后的校验本身查错了信号**（用户在 Colab 上实跑修复后的
  `01_data_prep.ipynb`时发现）。自然时长修复上线后，notebook 里那道"末尾是否
  还在说话"的校验对 120 条抽查报出 **65 条（54%）疑似截断**——乍看像是修复没生效，
  排查后发现是**假警报**：那道校验查的是写盘的 `clean` 字段，也就是**混响后**
  的参考音频（测试集主表固定 T60=0.3，占了绝大多数样本）。`apply_rir()` 用
  FFT 卷积实现混响，卷积结果被裁到跟干信号等长（见其 docstring "输出长度与
  输入相同"），这意味着参考音频末尾**必然**带着一段真实的混响拖尾——语音

  真正的确认要等新数据回来后看 T60=0 那组是否为 0。

- **教训（叠加上一条）**：验证脚本本身也可能有 bug，而且这类 bug 特别隐蔽——
